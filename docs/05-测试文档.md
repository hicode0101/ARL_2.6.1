# ARL 测试文档

| 项目 | 内容 |
|---|---|
| 测试代码位置 | `test/`（48 个 `.py` 文件） |
| 测试框架 | unittest（`unittest.TestCase`，兼容 pytest 收集） |
| 测试性质 | **依赖真实环境的集成测试**（需 MongoDB / Celery / 外网 / 预置数据），非纯单元测试 |
| CI 现状 | 无自动化测试流水线；`.github/workflows` 仅有镜像构建与发布（构建期以 `flask routes`、`python3 -m app.celerytask` 做冒烟自检） |

---

## 1. 测试体系组织

### 1.1 文件分类

| 类别 | 文件 | 运行方式 |
|---|---|---|
| 聚合入口 | `test/main.py` | `unittest.defaultTestLoader.discover(pattern="test_*.py")` + `TextTestRunner(verbosity=2)`，**仅发现 `test_*.py` 命名文件** |
| 标准用例（44 个） | `test/test_*.py` | 单文件：`python3.6 -m test.test_xxx`；或 `pytest test/test_xxx.py` |
| 端到端驱动脚本（4 个，不以 test_ 开头，discover 不收集） | `test/ip.py`、`test/task.py`、`test/scheduler.py`、`test/sync_asset.py` | 直接 `python3.6 -m test.task` 运行；逻辑为「向 MongoDB 插任务 + 调用 `celerytask.arl_task()` 端到端执行 + 断言结果入库」 |

### 1.2 环境依赖

| 依赖 | 说明 |
|---|---|
| MongoDB | 大量用例直接读写 `task/site/domain/ip/fingerprint/result_set` 等集合 |
| RabbitMQ / Celery | 驱动脚本与部分用例直接投递 / 执行 Celery 任务 |
| 外网连通 | 用例大量访问 `baidu.com`、`qq.com`、`jd.com`、`taobao.com`、`example.com`、`1.1.1.1`、`8.8.8.8` 等 |
| 预置数据 | 多个用例硬编码历史环境中的 `task_id` / `scope_id` / `scheduler_id`（如 `61513c9f6591e704f896b175`），库中无对应数据时用例失败或空跑 |
| 密钥配置 | `test_fofa.py`（需 FOFA EMAIL/KEY）、`test_github_search.py`（需 GITHUB.TOKEN）、`test_utils_push.py`（需钉钉 / 邮件 / 飞书 / 企微配置）、`test_webhook.py`（需 WEBHOOK.URL）、`test_proxy_url.py`（需 PROXY.HTTP_URL） |
| 外部工具 | nmap、nuclei、wih、massdns、phantomjs 需已在 PATH（按用例） |

> 结论：该测试集适合**开发者在自建环境做功能回归**，不能在新部署上开箱即跑。

## 3. 典型运行方法

```bash
# 前提：ARL 已按《06-程序部署文档》安装，config.yaml 已配置
cd /opt/ARL

# 1) 运行全部可发现的用例（依赖环境齐全，否则大量失败）
python3.6 -m test.main
# 或 pytest test/

# 2) 运行单个用例
python3.6 -m test.test_expr            # 纯逻辑，任何环境可跑
python3.6 -m test.test_policy_edit     # 纯逻辑
python3.6 -m test.test_cdn             # 仅需本地字典

# 3) 带参数的用例
python3.6 -m test.test_query_plugin crtsh alienvault   # 指定数据源
python3.6 -m test.test_webhook <task_id> <scope_id>

# 4) 端到端驱动脚本（直接写库执行任务）
python3.6 -m test.task
python3.6 -m test.ip
```

> 容器内运行：`docker-compose exec worker bash` 后进入 `/code` 执行上述命令。

## 4. 冒烟测试清单（部署验收用）

针对「新部署环境是否正常」推荐按序执行以下手工验收（不依赖预置数据）：

| # | 步骤 | 通过标准 |
|---|---|---|
| 1 | 浏览器访问 `https://<IP>:5003` | 出现登录页（自签证书需信任） |
| 2 | admin / arlpass 登录 | 进入任务页面；`/api/doc` 可打开 Swagger |
| 3 | 下发测试任务：目标 `example.com`，仅开 `domain_brute(test)` + `port_scan(test)` | 任务状态流转至 done，`service` 数组有各阶段耗时 |
| 4 | 任务详情页查看站点 / 域名 / IP 标签页 | example.com 相关数据存在 |
| 5 | 开启 `site_capture` 重跑 | 站点列表截图列可显示图片（验证 phantomjs + 截图接口） |
| 6 | 创建资产组（scope=example.com）→ 任务详情「同步到资产组」 | 资产域名 / 站点出现数据 |
| 7 | `GET /api/console/info` | 返回 CPU / 内存 / 磁盘数据 |
| 8 | `python3.6 -m test.test_expr`（容器内） | 全部通过（验证 Python 环境完整） |
| 9 | 重启全部容器 / 服务后再次登录 | 数据仍在（Mongo 卷持久化生效） |

## 5. 测试体系评估与改进建议

1. **纯逻辑用例极少**：仅 `test_expr`、`test_policy_edit`、`test_utils`（部分）、`test_normal_url` 等不依赖外部环境；建议把枚举 / 错误码 / 工具函数 / 查询构造器（`build_db_query`）等补齐为可 CI 化单测；
2. **强耦合预置 ID**：大量硬编码 task_id/scope_id 建议改为 setUp 中动态创建 + tearDown 清理；
3. **副作用明显**：`test_utils_push` 等会真实发送消息，建议增加 mock 开关；
4. **无 API 层自动化**：REST 接口无端到端用例，可基于 `/api/doc` 的 flask-restx 模型生成契约测试；
5. **无安全测试**：认证 / 黑名单（SSRF）仅有零散断言（`test_check_domain_black`），建议补充 `BLACK_IPS` 拦截、`AUTH=false` 行为、无鉴权 image 接口的回归用例。
