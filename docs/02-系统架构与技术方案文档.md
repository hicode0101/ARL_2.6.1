### 2.2 进程模型与入口

| 进程 | 入口文件 | 生产启动命令 | 职责 |
|---|---|---|---|
| Web API | `app/main.py`（`arl_app`） | `gunicorn -b 0.0.0.0:5003 app.main:arl_app -w 3`（容器内，前置 nginx）/ `gunicorn -b 127.0.0.1:5013`（源码部署） | REST API、Swagger、启动时执行 `arl_update()` 数据库升级 |
| Worker（常规） | `app/celerytask.py` | `celery -A app.celerytask.celery worker -Q arltask -n arltask -c 2 -O fair` | 执行资产发现 / 风险巡航 / 监控 / 同步等任务 |
| Worker（GitHub） | 同上 | `celery ... -Q arlgithub -n arlgithub -c 2 -O fair` | GitHub 泄漏搜索与监控（独立队列隔离慢任务） |
| Scheduler | `app/scheduler.py`（`run_forever`） | `python3.6 -m app.scheduler` | 周期轮询 `scheduler`（资产监控）、`github_scheduler`（GitHub 监控）、`task_schedule`（计划任务）三个集合并投递任务，主循环 `sleep(58)` |

Celery 关键配置（`app/celerytask.py`）：`task_acks_late=False`、`worker_prefetch_multiplier=1`、broker 重连 `max_retries=3`；`platforms.C_FORCE_ROOT=True`。任务分发函数 `run_task()` 按 `options["celery_action"]` 路由到 12 类动作（`CeleryAction` 枚举）：`ip_task / domain_task / domain_exec_task / ip_exec_task / domain_task_sync_task / run_risk_cruising / fofa_task / github_task_task / github_task_monitor / asset_site_update / add_asset_site_task / asset_wih_update`。

SIGTERM 信号经 `exit_gracefully()` 用 psutil 递归终止 massdns / nmap / nuclei 等子进程树，避免残留。

## 3. 关键技术方案

### 3.1 任务下发与执行链路

```
用户 → POST /api/task/ (routes/task.py, reqparse 校验)
     → helpers/task.py: get_ip_domain_list()   目标合法性+黑名单校验（防SSRF/禁扫域名）
     → build_task_data()                        构造 task 文档(status=waiting)
     → submit_task(): insert task → celerytask.arl_task.delay(options) → 回写 celery_id
                                                  (投递失败则删除任务记录, 回滚)
     → RabbitMQ(arltask 队列) → worker: run_task() 按 celery_action 分发
     → tasks/domain.py: DomainTask.run() / tasks/ip.py: IPTask.run()
     → 各阶段: update_task_field 更新 task.status 为当前阶段名; update_services 记录耗时
     → CommonTask.common_run(): 指纹统计/C段统计/任务统计 → sync_asset → push → status=done
```

设计要点：

- **任务即文档**：任务元数据、状态、进度、阶段耗时、统计全部内聚在 `task` 集合一个文档中，无独立 task_trace 表；
- **选项透传**：API 参数与策略展开后的选项统一放入 `task.options`，任务执行器只读 `options`，实现「策略 / 计划任务 / 监控 / 手工下发」四条入口共用一套执行器；
- **单飞并发**：`worker_prefetch_multiplier=1` + 每队列并发 2，长任务不会饿死队列；
- **一键重跑**：重启任务复制原文档重新投递（名称加前缀「重新运行-」）。

### 3.2 域名任务执行流水线（DomainTask）

`app/tasks/domain.py: DomainTask.run()`，按五大阶段顺序编排（每阶段受 `options` 开关控制）：

1. **domain_fetch 域名收集**
   - 域名爆破：随机子域探测泛解析 IP 集合 → 按字典档位取词 → massdns（`-o S -r dicts/dnsserver.txt -s <并发>`，普通 300 / altDNS 1500）→ 多线程 A 记录解析（并发 15）→ 过滤泛解析（命中随机子域 IP 集，或同一 record 出现 >35 次）→ 入 `domain` 集合（source=domain_brute）；
   - 域名插件：12 源并发查询，统一过滤（去 `*.`、长度差 <25、合法性、黑名单）后按 source 入库；
   - ARL 历史查询：从历史 `task/domain` 与 `asset_scope/asset_domain` 提取 `*.目标` 子域复用；
   - altDNS：`DnsGen` 五种变换（插词 / 插数字 1-3 位 / 前后缀拼接 / 同义词替换）生成组合域名二次 massdns，同一 record ≥15 次剔除；子域超 800（或有泛解析且超 300）自动跳过；
   - 搜索引擎：百度（rn=100）+ Bing 抓取 `site:domain`，新子域入库，非首页 URL 取标题后入 `url` 集合；
   - `{fuzz}` 占位符目标仅做模糊字典替换爆破。
2. **start_ip_fetch IP 整理**：构建 IP↔域名映射 → CDN 判定（`dicts/cdn_info.json` IP 段 / CNAME 后缀 / 关键字 / 多 A 记录启发，可跳过 CDN IP）→ nmap 扫描（`-sT -n --open`，服务识别 `-sV`、OS `-O`，全端口档自动调优 min-rate≥800/parallelism≥128/存活探测；单主机 >600 开放端口仅留 80/443）→ 入 `ip` 集合（公网 IP 附 geo_asn/geo_city、ip_type、cdn_name）→ SSL 证书抓取入 `cert` → 服务聚合入 `service`。
3. **start_site_fetch 站点发现**：域名 × 开放端口构造 URL → `check_http` 探活（并发 15，剔除 400/5xx/拦截页；未开端口扫描时用 `probe_http` 直探 http/https）→ `WebSiteFetch` 流水线：
   `fetch_site`（title/status/headers/Server/body_length/favicon(mmh3)、双引擎指纹、自动打标「入口/无效」→ 入 `site`）→ `site_identify`（phantomjs+Wappalyzer）→ `site_capture`（phantomjs 截图至 `tmp_screenshot/<task_id>/`）→ `site_spider`（静态爬虫，a/form/iframe，深度 5，相似 URL 哈希去重 → `url`）→ `file_leak`（→ `fileleak`）→ `nuclei_scan`（→ `nuclei_result`）→ `web_info_hunter`（wih 二进制 → `wih`）。
4. **风险检测**：findvhost（内网域名 × 公网 IP 的 Host 碰撞，404 基线相似度 0.9 → `vuln`）→ npoc 协议识别（→ `npoc_service`）→ PoC 扫描 / 弱口令（xing 插件框架，并发 10，进度实时回写 → `vuln`）。
5. **收尾**：WIH 新域名回补（解析+抓站）→ 统计（`stat_finger`/`cip`/`task.statistic`）→ `sync_asset`（有 related_scope_id 时）→ 消息推送 → `status=done`（异常置 `error`）。

监控变体 `DomainExecutor`（`app/tasks/scheduler.py`）：复用同一流水线，差异在于——自建任务文档（task_tag=monitor）、收集完成后与资产库已有域名做**差集仅保留新增**（二次随机子域校验泛解析）、只把新域名以 source=monitor 重存、结束后 `sync_asset(update_flag=True, push_flag=True)` 并触发 WebHook。

### 3.3 IP 任务流水线（IPTask）

`app/tasks/ip.py`：nmap 扫描（目标按空格拆分）→ geoip/类型标注 → 服务入库 → SSL 证书 → find_site（ip:port 构造 URL 探活）→ WebSiteFetch → 协议识别 → PoC/弱口令 → 统计 → 同步。监控变体 `IPExecutor` 增量逻辑：加载资产库已有 `{ip: port集合}` 映射，仅新 IP 入 `ip` 表、新 IP/新端口增量合并入 `asset_ip`。

### 3.4 调度进程方案（scheduler）

`app/scheduler.py: run_forever()` 每 58 秒一轮（注释说明须 <60s，否则 GitHub cron 可能错过触发窗口），三轮调度：

1. **资产监控**：遍历 `scheduler` 集合（status=running 且 next_run_time 到期），按 `scope_type` 分派：domain → `DOMAIN_EXEC_TASK`、ip → `IP_EXEC_TASK`、site_update_monitor → 站点更新任务、wih_update_monitor → WIH 更新任务；投递后刷新 `last_run/next_run/run_number`；
2. **GitHub 监控**：遍历 `github_scheduler`，`crontab.CronTab` 计算下次触发 <60s 且距上次运行 >180s 才执行（防重复）；
3. **计划任务**：遍历 `task_schedule`，`recurrent_scan`（cron）与 `future_scan`（start_time 到期）分别处理，按 policy_id 展开选项后走 `submit_task_task / submit_risk_cruising`。

### 3.5 指纹识别引擎（双规则源）

```
站点响应 → fetch_fingerprint()               内置规则 dicts/webapp.json
        → finger_db_identify()               自定义规则（fingerprint 集合, 进程内缓存）
              └→ expr.py 表达式引擎（pyparsing）：
                 变量 body/title/header/icon_hash；运算符 =(包含)/==/!=/&&/||/!
                 规则解析结果按 MD5 缓存
        → 合并去重 → site.finger 数组
```

`site_identify` 开启时另用 phantomjs + Wappalyzer（`tools/driver.js`、`apps.json`）做 JS 层识别并合并，单站超时 20s、并发 3。

### 3.6 插件化设计

- **域名查询插件**：`app/services/dns_query_plugin/` 每源一个文件，实现 `source_name / init_key(**kwargs) / sub_domains(target)`；`query_loader` 用 importlib 动态加载；基类统一做结果过滤与去重；密钥与开关由 `QUERY_PLUGIN` 配置段下发（全空参数自动跳过）。
- **PoC 插件**：外部框架 ARL-NPoC（`xing.core.PluginRunner`），插件分 POC / BRUTE / SNIFFER 三类；元数据经 `sync_to_db()` 同步 `poc` 集合；用户 PoC 目录 docker 挂载 `./poc`；`GET /api/poc/sync/` 重同步（含下架清理）。
- **消息推送通道**：`app/utils/push.py` 钉钉（加签）/ 飞书（加签）/ 企业微信 / SMTP 四通道统一入口 `message_push()`，未配置自动跳过。
- **WebHook**：`app/services/webhook.py` 域名 / IP / 站点三类资产变化聚合推送（POST JSON，Header `Token: WEB_HOOK_TOKEN`，每类限 100 条）。

### 3.7 资产同步算法（syncAsset）

`app/services/syncAsset.py`，把任务结果（site/domain/ip/wih）合并入资产库（asset_*）：

- 查重键：site/domain/ip 用 `{scope_id, <类别>: 值}`，wih 用 `{scope_id, fnv_hash}`；
- site 特殊处理：URL 含 `?`/`;` 时截断后按前缀正则粗判去重；
- 不存在 → 插入（补 scope_id/save_date/update_date），并计入新资产推送样例（每类上限 10 条）；
- 已存在且 `update_flag=True`（监控路径）→ 整文档替换，保留原 save_date、刷新 update_date，ip 类合并新旧 domain 数组；
- 手动 / 自动路径（update_flag=False）已存在记录不更新。

### 3.8 认证与安全设计

| 机制 | 实现 | 说明 |
|---|---|---|
| 登录认证 | `app/utils/user.py` | 口令校验 `md5('arlsalt!@#' + 明文)`；token=`md5(50位随机串)` 存 `user.token`；单 Token 模式（新登录覆盖、改密登出、无过期时间） |
| 请求鉴权 | `@auth` 装饰器（除 login 与 image 外全部端点） | Header `Token`（兼容 `?token=`）；优先级：`AUTH=false` 直接放行 → 等于 `API_KEY` 以 ARL-API 身份放行 → 查库校验 |
| SSRF 防护 | `ARL.BLACK_IPS` + `not_in_black_ips()` | 任务目标过滤回环 / 内网段（默认 127/8、0/8，docker 配置加 172.16/12、100.64/10） |
| 禁扫保护 | `blackdomain.txt`/`blackhexie.txt` + `FORBIDDEN_DOMAINS` | 域名黑名单与禁扫后缀（默认 gov.cn/edu.cn/org.cn） |
| 传输安全 | Nginx TLS1.2/1.3 + HSTS + 自签证书（`gen_crt.sh`，CN=127.0.0.1，10 年） | 对外仅 443（宿主映射 5003） |
| 已知弱点 | `/api/image/` 无鉴权；`AUTH=false` 全站匿名；MD5 加盐弱哈希；token 永不过期 | 部署安全基线中必须整改前两项 |

### 3.9 配置体系

- 代码内 `Config` 类（`app/config.py`）提供全部默认值；`app/config.yaml`（由 `config.yaml.example` 复制修改）在进程启动时覆盖；解析失败 `sys.exit(-1)`（fail-fast）。
- 配置分组：`CELERY`（broker）、`MONGO`（连接与库名）、`QUERY_PLUGIN`（12 源开关与密钥）、`GEOIP`、`FOFA`、`ARL`（AUTH/API_KEY/BLACK_IPS/FORBIDDEN_DOMAINS/字典路径/并发数/自定义端口）、`DINGDING/EMAIL/FEISHU/WXWORK/WEBHOOK`（推送）、`GITHUB.TOKEN`、`PROXY.HTTP_URL`。
- 代码内置不可配置项：TOP_1000/TOP_100 端口串、`DOMAIN_MAX_LEN=25`、字典与规则文件路径、`app/tmp`、`app/tmp_screenshot`。

### 3.10 前端方案

`docker/frontend/` 为编译后的 Vue 2 + ant-design-vue SPA（webpack 产物，含 taskList/taskDetail/taskFofa/assetsMonitor/groupAssetsManagement/pocList/search 等页面 chunk）。Nginx `try_files` 托管，`/api/` 反代 gunicorn；登录后 token 存 `localStorage`，axios 拦截器统一注入 `token` 请求头。

### 3.11 构建与发布（CI/CD）

`.github/workflows/`：`builder.yml`（手动触发，构建 amd64 镜像 `tophant/arl:<version>`）、`arm-builder.yml`（QEMU+Buildx 构建 arm64，tag `arm-<version>`）、`push-docker-manifest.yml`（合成多架构 manifest 与 latest）、`release.yml`（push tag `v*` 触发，打包 docker.zip——compose、config-docker.yaml、mongo-init.js、.env、日志占位文件——上传 Release）。构建前镜像自检：`flask routes` 校验应用可加载、`python3 -m app.celerytask` 校验 worker 可导入。

## 4. 架构评估与改进建议（面向二次开发）

| 观察点 | 现状 | 建议 |
|---|---|---|
| 认证强度 | MD5 固定盐、token 无过期、单 token | 引入 bcrypt/argon2 与 token TTL/刷新机制 |
| 截图接口 | `/api/image/` 无鉴权 | 加 `@auth` |
| 数据生命周期 | 无 TTL/归档，`github_hash`、`result_set` 只增不减 | 对结果类集合按任务时间建 TTL 索引或定期归档 |
| 测试 | 集成测试强依赖真实环境与预置数据，无 CI 测试 | 抽离纯逻辑单测（expr/policy/cdn/url 等）进 CI |
| 依赖 | phantomjs 已停止维护、Python 3.6 EOL | 评估 playwright/chrome 替代截图；升级 Python 基线 |
| 部署 | systemd unit 无 Restart 策略；compose 无 healthcheck | 增加 `Restart=on-failure` 与健康检查 |
| 密钥管理 | 数据库 / MQ 口令硬编码于 compose 与配置样例 | 引入 secrets/env 注入并轮换 |
